Background

e-HR은 계열사 임직원이 인사 정보 조회, 전자 결재, 입사자 등록 같은 업무에 쓰는 인사 시스템입니다. Java와 Spring, JSP, Oracle로 만들어진 시스템을 2023년부터 혼자 운영하고 있습니다.

e-HR is the HR system that employees of an affiliate use for looking up HR records, electronic approval and registering new hires. I have run this Java, Spring, JSP and Oracle system on my own since 2023.

Problem

핵심 화면의 응답이 최대 18초에 달해 현업의 불만이 이어졌습니다. 배포는 파일을 하나씩 FTP로 올리는 방식이라, 운영서버에서 직접 고친 파일이 저장소에 없거나 저장소와 다른 경우가 쌓여 있었습니다.

Key screens took up to 18 seconds, and users kept complaining. Deploys meant uploading files one by one over FTP, so fixes made directly on the production server were missing from the repository or differed from it.

What I did

빌드와 배포 파이프라인 전환Build and deploy pipeline
SVN 저장소를 GitLab으로 옮기고 Gradle 빌드를 도입했습니다. 운영서버에만 있던 수정분 900여 건을 저장소에 반영해 둘을 맞춘 뒤, Jenkins로 개발서버 자동 배포와 운영용 WAR·변경 목록 자동 생성을 구성했습니다. 배포 사고를 막는 장치도 넣었습니다. 환경별 설정 폴더가 없으면 빌드가 실패해 기본값이 섞인 WAR가 나가지 않고, WAR에 빌드 환경 표시를 넣어 운영용이 아니면 중단하며, 서버 업로드 폴더는 WAR에서 빼 덮어쓰지 않게 했습니다. 서버 파일은 JEUS 프로세스가 내려간 것을 확인한 뒤에만 교체합니다.I moved the SVN repository to GitLab and introduced a Gradle build. After bringing about 900 production-only changes into the repository, I set up Jenkins to deploy automatically to the development server and to build the production WAR with a change list. I also added guards against bad deploys: the build fails without the per-environment config, so no WAR ships with default settings; each WAR carries its build environment and the production step stops if it is not a production build; the server upload folder is kept out of the WAR so it is never overwritten; and files are replaced only after the JEUS process is confirmed down.
핵심 화면 응답 18초 → 1초 이내Key screen response, 18 s → under 1 s
인사기본 화면을 구간별로 측정해 보니 원인이 세 층에 흩어져 있었습니다. DB에서는 한 행마다 8번 불리던 공통코드 조회 함수를 코드 테이블 조인으로 바꾸고, 화면에 쓰지 않는 함수 호출과 컬럼을 걷어 냈습니다. 서버에서는 요청마다 DB에서 다시 읽던 뷰 정의와 메뉴별 마스킹 설정을 캐시에 두었습니다. 뷰 정의는 배포 때만 바뀌어 캐시가 어긋나지 않고, DDL을 바꾼 뒤 비울 수 있는 초기화 메서드도 두었습니다. 접속 기록은 법적 점검 대상이라 줄이지 않고, 요청마다 하던 DB 쓰기 4번을 전용 스레드 3개로 넘겨 화면이 기다리지 않게 했습니다. 화면에서는 직원 정보 헤더를 그리려고 동기로 세 번 부르던 설정 조회를 고정 항목 정의와 정적 쿼리 한 번으로 합치고, 공통코드는 브라우저(sessionStorage)에 저장해 비동기로 불러오게 했습니다. 이전에도 2024년부터 메인 화면의 결재 건수 COUNT 쿼리와 수당·공제 목록 조회 쿼리를 같은 방식으로 정리해 왔습니다.Timing the employee profile screen step by step showed the cause spread over three layers. In the database, a common-code lookup function called 8 times per row became joins on the code table, and function calls and columns the screen never used were removed. On the server, view definitions and per-menu masking settings that were re-read from the database on every request now come from a cache. View definitions change only on deploy, so the cache cannot drift, and a reset method clears it after a DDL change. Access logs are subject to legal audits, so instead of cutting them I moved the four database writes per request to three dedicated threads, so screens no longer wait. In the browser, three synchronous setting calls for the employee header became a fixed field definition and one static query, and common codes are kept in sessionStorage and loaded asynchronously. Since 2024 I had been cleaning up other everyday queries the same way, such as the approval-count queries on the main page and the allowance and deduction list.
운영 OOM 장애 원인 분석과 재발 방지Production OOM: root cause and prevention
2026년 10월 운영 서버(JVM 힙 1GB)가 OutOfMemoryError로 503 장애를 냈습니다. 장애 직전 호출을 추적해 개인별 일근무 조회가 두 차례 불린 것을 찾았습니다. 이 쿼리는 사번을 이름 LIKE '%사번%'로도 비교해, 사번이나 월이 비어 들어오면 전 사원·전 기간을 조회하고 결과 전체를 메모리에 올리고 있었습니다. 호출하는 화면이 모두 사번만 넘긴다는 것을 확인한 뒤 이름 LIKE 조건을 없애고, 사번이 일치하고 월이 6자리일 때만 조회하도록 막았습니다. 정상 호출의 결과는 그대로이고, 같은 입력으로는 다시 전체 조회가 일어나지 않습니다.In October 2026 the production server (1 GB JVM heap) hit an OutOfMemoryError and returned 503s. Tracing the calls right before the outage, I found the personal daily-attendance lookup had run twice. The query also matched the employee ID against the name with LIKE '%id%', so an empty ID or month pulled every employee for every period and loaded it all into memory. After confirming every calling screen passes only the employee ID, I removed the name LIKE and allowed the query only for an exact ID and a 6-digit month. Normal calls return the same results, and the same input can no longer trigger a full scan.
일괄 결재 병렬 처리Parallel bulk approval
한 건씩 차례로 처리하던 결재를 최대 5건씩 동시에 처리하도록 바꿨습니다(스레드 풀). DB 커넥션 풀을 넘지 않도록 동시 처리 수를 5로 제한했고, 건마다 DB에 현재 시각을 묻던 호출을 없앴습니다.Approvals handled one at a time now run up to 5 at once (a thread pool). I capped it at 5 to stay within the database connection pool, and removed the database call that fetched the current time for every item.
개인정보 공통 마스킹과 해제 로그Shared personal data masking and unmask logs
화면마다 따로 하던 마스킹을 공통 인터셉터 하나로 모으고, 메뉴별로 마스킹 여부를 설정할 수 있게 했습니다. 마스킹을 해제하면 기록이 남고, 그 기록을 조회할 수 있습니다. 로그인(IP 포함), 메뉴 사용, 데이터 조회 로그도 남기도록 개선해, 매월 개인정보처리시스템 접속기록 점검 자료로 제출합니다.I moved masking into one shared interceptor and made it configurable per menu. Every unmask is logged, and the log can be searched. I also improved logging of logins (with IP), menu use and data queries, which feed the monthly access-record audit of the personal data system.
SSO 통합 로그인 PLSingle sign-on project leader
SSO 인증 연동의 분석, 설계, 개발, 검증을 이끌었습니다.I led analysis, design, development and verification of the SSO integration.
입사자 등록 자동화Automated new hire registration
수기 입력을 엑셀 업로드, 유효성 검증, DB 자동 반영으로 이어지는 구조로 바꿨습니다. 이후 가족과 학력 정보도 같은 방식으로 올릴 수 있게 넓혔습니다.I replaced manual entry with Excel upload, validation and automatic database updates, and later extended it to family and education records.
법정 패치 20회 이상 적용20+ statutory patches applied
연말정산을 비롯한 법정 패치를 20회 이상 적용했습니다.I applied more than 20 statutory patches, including year-end tax settlement.

Result

핵심 화면 응답을 18초에서 1초 이내로 줄였고, 지금도 단독으로 운영하고 있습니다.

Key screen response went from 18 seconds to under 1 second, and I still run the system on my own.
