Background

e-HR은 계열사 임직원 약 500명이 인사 정보 조회, 전자 결재, 입사자 등록 같은 업무에 쓰는 인사 시스템입니다. Java와 Spring, JSP, Oracle로 만들어진 시스템을 2023년부터 혼자 운영하고 있습니다.

e-HR is the HR system that about 500 employees of an affiliate use for looking up HR records, electronic approval and registering new hires. I have run this Java, Spring, JSP and Oracle system on my own since 2023.

Problem

핵심 화면의 응답이 18초에 달했습니다. 수기 입력과 FTP 수동 배포 때문에 오류와 오배포의 위험도 쌓이고 있었습니다.

The response of the key screens reached 18 seconds. Manual data entry and manual FTP deploys were also piling up the risk of errors and bad releases.

Why this approach

응답 지연을 어떻게 없앨 것인가

How to remove the response delay

대안장점한계결론
서버 스펙 증설코드 변경이 없음원인이 쿼리 해석과 반복 조회라 효과가 적음제외
인덱스 보완만위험이 낮음매번 쿼리를 해석하는 비용이 남음1단계로 적용
쿼리 고정 + 데이터 저장(캐시) + 접속 기록 분리해석, 조회, 기록 부담을 한꺼번에 줄임저장한 데이터를 언제 지울지 규칙이 필요최종 채택
OptionUpsideLimitDecision
Bigger serversNo code changeThe cause is query re-reading and repeated fetches, so the gain is smallRejected
Indexes onlyLow riskThe cost of re-reading each query remainsUsed as step 1
Fixed queries + stored data (cache) + separate access logsCuts re-reading, fetching and logging cost at onceNeeds rules for when stored data is clearedChosen

What I did

핵심 화면 응답 18초 → 1.0초 (94% 감소)Key screen response, 18 s → 1.0 s (94% less)
먼저 DB 분석 리포트(AWR)와 브라우저 개발자 도구로 원인을 찾았습니다. 화면을 열 때마다 DB가 쿼리를 처음부터 다시 해석하고(하드파싱), 같은 데이터를 반복해서 읽고 있었습니다. 그래서 쿼리를 미리 고정해 재사용하게 하고, 찾기 쉽도록 색인(인덱스)을 보완하고, 자주 쓰는 데이터는 서버에 저장해 두었습니다(캐시, 요청의 87%를 여기서 처리). 접속 기록은 화면 응답을 기다리지 않고 따로 남기게 했습니다.I first used database reports (Oracle AWR) and browser dev tools to find the cause. Every time a screen opened, the database re-read the query from scratch (hard parsing) and fetched the same data again. So I fixed the queries in advance so they are reused, added indexes, and kept frequently used data on the server (a cache that answers 87% of requests). Access logs are now written separately, without holding up the screen.
일괄 결재(최대 300건) 14초 → 1초 이내Bulk approval (up to 300 items), 14 s → under 1 s
한 건씩 차례로 처리하던 결재를 8개씩 동시에 처리하도록 바꿨습니다(스레드 풀). 한 문서 안의 결재 순서가 뒤섞이지 않도록 문서마다 잠금을 걸었습니다.Approvals handled one at a time now run 8 at once (a thread pool). Each document is locked so its approval order never gets mixed up.
SSO 통합 로그인 PL (5인, 4개월)Single sign-on project leader (5 people, 4 months)
대상 시스템 6개의 분석, 설계, 개발, 검증을 이끌었습니다. 로그인 관련 문의가 월 12건에서 2건으로 줄었습니다.I led analysis, design, development and verification across 6 systems. Login inquiries fell from 12 to 2 a month.
입사자 등록 20분 → 1분 (월 약 13시간 절감)New hire registration, 20 min → 1 min (about 13 hours saved a month)
엑셀 업로드, 유효성 검증, DB 자동 반영으로 이어지는 구조로 바꿨습니다.I replaced manual entry with Excel upload, validation and automatic database updates.
개인정보 마스킹 62개 화면 일원화Personal data masking unified across 62 screens
공통 AOP와 인터셉터로 처리해 누락이 0건입니다. 권한 등급별 해제, 접근 로그, 감사 추적을 갖췄고 내부 개인정보 점검에서 지적이 없었습니다.A shared AOP aspect and interceptor handle masking, with no screen missed. Unmasking by permission level, access logs and an audit trail are in place, and the internal privacy audit raised no findings.
배포 40분 → 6분, 오배포 연 3건 → 0건Deploy time, 40 min → 6 min; bad releases, 3 a year → 0
FTP 수동 배포를 Jenkins와 Git 파이프라인으로 바꿨습니다. Gradle 빌드를 도입하고, 운영서버와 저장소의 차이 900여 건을 정합화했습니다.I replaced manual FTP deploys with a Jenkins and Git pipeline, introduced a Gradle build, and reconciled about 900 differences between the production server and the repository.
법정 패치 20회 이상 적용20+ statutory patches applied
연말정산을 비롯한 법정 패치를 20회 이상 적용했습니다.I applied more than 20 statutory patches, including year-end tax settlement.

Result

핵심 화면 5종의 응답을 개선 전후 각 2주씩 비교했습니다. 연 12회 이상 무중단 배포를 하며 단독으로 운영하고 있습니다.

I compared the response of the 5 key screens over two weeks before and after. I run the system alone, with 12 or more zero-downtime deploys a year.

Measurement & trade-offs

측정Measurement
응답 시간은 브라우저 개발자 도구(Chrome DevTools)로 쟀고, DB가 쿼리를 새로 해석한 횟수는 DB 분석 리포트(AWR)로 개선 전후를 비교했습니다.Response time was measured with browser dev tools (Chrome DevTools). How often the database re-read queries from scratch was compared before and after with database reports (Oracle AWR).
트레이드오프Trade-off
저장해 둔 데이터 때문에 바뀐 내용이 화면에 최대 30초 늦게 보입니다. 인사 데이터는 그 정도 늦어도 괜찮아서, 현업과 합의한 뒤 받아들였습니다.Because of the stored data, a change can show up to 30 seconds late. HR data can wait that long, so I accepted it after agreeing with the business side.
