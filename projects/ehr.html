Background

e-HR은 계열사 임직원 약 500명이 인사 정보 조회, 전자 결재, 입사자 등록 같은 업무에 쓰는 인사 시스템입니다. Java와 Spring, JSP, Oracle로 만들어진 시스템을 2023년부터 혼자 운영하고 있습니다.

e-HR is the HR system that about 500 employees of an affiliate use for looking up HR records, electronic approval and registering new hires. I have run this Java, Spring, JSP and Oracle system on my own since 2023.

Problem

핵심 화면의 p95 응답이 18초에 달했습니다. 수기 입력과 FTP 수동 배포 때문에 오류와 오배포의 위험도 쌓이고 있었습니다.

The p95 response of the key screens reached 18 seconds. Manual data entry and manual FTP deploys were also piling up the risk of errors and bad releases.

Why this approach

응답 지연을 어떻게 없앨 것인가

How to remove the response delay

대안장점한계결론
서버 스펙 증설코드 변경이 없음병목이 하드파싱과 반복 조회라 효과가 제한적제외
인덱스 보완만위험이 낮음동적 SQL의 파싱 비용이 남음1단계로 적용
정적 SQL + 서버 캐시 + 로그 비동기파싱, 조회, I/O 부담을 함께 제거캐시 무효화 규칙이 필요최종 채택
OptionUpsideLimitDecision
Bigger serversNo code changeThe bottleneck is hard parsing and repeated queries, so the gain is limitedRejected
Indexes onlyLow riskThe parsing cost of dynamic SQL remainsUsed as step 1
Static SQL + server cache + async loggingRemoves parsing, query and I/O cost togetherNeeds cache invalidation rulesChosen

What I did

핵심 화면 응답 18초 → 1.0초 (94% 감소)Key screen response, 18 s → 1.0 s (94% less)
AWR과 개발자 도구로 병목이 하드파싱과 반복 조회임을 먼저 특정했습니다. 그다음 동적 SQL 정적화, 인덱스 보완, 서버 캐시(적중률 87%), 접속 로그 비동기 분리를 적용했습니다.I first used Oracle AWR and browser dev tools to pin the bottleneck on hard parsing and repeated queries. Then I made dynamic SQL static, added indexes, added a server cache (87% hit rate) and moved access logging off the request path.
일괄 결재(최대 300건) 14초 → 1초 이내Bulk approval (up to 300 items), 14 s → under 1 s
건별 직렬 처리를 스레드 풀 8개의 비동기 병렬 처리로 바꿨습니다. 결재선 순서는 문서 단위 락으로 보장했습니다.I replaced one-by-one processing with asynchronous work on a pool of 8 threads. A per-document lock keeps the approval order correct.
SSO 통합 로그인 PL (5인, 4개월)Single sign-on project leader (5 people, 4 months)
대상 시스템 6개의 분석, 설계, 개발, 검증을 이끌었습니다. 로그인 관련 문의가 월 12건에서 2건으로 줄었습니다.I led analysis, design, development and verification across 6 systems. Login inquiries fell from 12 to 2 a month.
입사자 등록 20분 → 1분 (월 약 13시간 절감)New hire registration, 20 min → 1 min (about 13 hours saved a month)
엑셀 업로드, 유효성 검증, DB 자동 반영으로 이어지는 구조로 바꿨습니다.I replaced manual entry with Excel upload, validation and automatic database updates.
개인정보 마스킹 62개 화면 일원화Personal data masking unified across 62 screens
공통 AOP와 인터셉터로 처리해 누락이 0건입니다. 권한 등급별 해제, 접근 로그, 감사 추적을 갖췄고 내부 개인정보 점검에서 지적이 없었습니다.A shared AOP aspect and interceptor handle masking, with no screen missed. Unmasking by permission level, access logs and an audit trail are in place, and the internal privacy audit raised no findings.
배포 40분 → 6분, 오배포 연 3건 → 0건Deploy time, 40 min → 6 min; bad releases, 3 a year → 0
FTP 수동 배포를 Jenkins와 Git 파이프라인으로 바꿨습니다. Gradle 빌드를 도입하고, 운영서버와 저장소의 차이 900여 건을 정합화했습니다.I replaced manual FTP deploys with a Jenkins and Git pipeline, introduced a Gradle build, and reconciled about 900 differences between the production server and the repository.
법정 패치 20회 이상 적용20+ statutory patches applied
연말정산을 비롯한 법정 패치를 20회 이상 적용했습니다.I applied more than 20 statutory patches, including year-end tax settlement.
바인드 변수 적용Bind variables
조건에 따라 문자열을 이어 붙이던 SQL을 바인드 변수를 쓰는 정적 SQL로 바꿔, 같은 실행 계획을 재사용하게 했습니다.SQL that was built by concatenating strings per condition became static SQL with bind variables, so the same execution plan is reused.
캐시 무효화 규칙Cache invalidation
인사 데이터가 바뀌면 해당 캐시를 지우고, 그 외에는 최대 30초 뒤 만료되게 했습니다. 코드성 데이터처럼 자주 조회되고 드물게 바뀌는 것부터 캐시에 올렸습니다.A change to HR data clears the matching cache entry, and everything else expires within 30 seconds. I cached frequently read, rarely changed data such as code tables first.

Hard parts

  • 오래된 시스템이라 동적 SQL이 화면마다 다른 방식으로 짜여 있었습니다. 핵심 화면 5종부터 순서대로 바꿨습니다.In an old system, dynamic SQL was written differently on every screen. I converted the 5 key screens first, in order.
  • 병렬 처리로 바꾸면서 결재선 순서가 뒤바뀔 위험이 생겼습니다. 문서 단위 락으로 한 문서 안의 순서를 지켰습니다.Going parallel risked scrambling the approval order. A per-document lock keeps the order within each document.

Result

핵심 화면 5종의 평균 응답을 개선 전후 각 2주의 일평균으로 비교했습니다. 연 12회 이상 무중단 배포를 하며 단독으로 운영하고 있습니다.

I compared the average response of the 5 key screens using daily averages over two weeks before and after. I run the system alone, with 12 or more zero-downtime deploys a year.

Measurement & trade-offs

측정Measurement
p95 응답은 Chrome DevTools의 Network 탭 기준이고, 하드파싱 횟수는 Oracle AWR 리포트로 개선 전후를 비교했습니다.p95 response is from the Chrome DevTools Network tab. Hard parse counts were compared before and after using Oracle AWR reports.
트레이드오프Trade-off
서버 캐시 때문에 갱신이 최대 30초 늦어집니다. 인사 데이터의 특성을 고려해 현업과 합의한 뒤 받아들였습니다.The server cache delays updates by up to 30 seconds. Given the nature of HR data, I accepted this after agreeing it with the business side.

What I learned

  • 서버를 늘리기 전에 병목을 재는 것이 먼저라는 것을 다시 확인했습니다.It confirmed again that measuring the bottleneck comes before adding servers.
  • 혼자 운영하는 시스템에서는 자동화가 곧 안정성이었습니다.On a system run by one person, automation is what stability means.
